# 人机对局与复盘模块

| 编号 | 需求 | 验收 |
|---|---|---|
| GAME-01 | 从可读非归档版本创建，选择先后手 | 两名明牌参与者 USER/BOT；绑定不可变快照 |
| GAME-02 | 仅当前用户座位可手动行动 | 所有权、版本、轮次、首手不可 PASS、合法性全部校验 |
| GAME-03 | 机器人异步行动 | 计算不阻塞 HTTP；陈旧版本结果丢弃 |
| GAME-04 | 明确最优与限时训练 | `TRAINING` 使用启发式，`OPTIMAL` 每个机器人回合实时求解并要求 `PROVEN`，预算不足时暂停 |
| GAME-05 | 结束、放弃和重开 | 终态只读；重开恢复同一对局的不可变初始快照，旧行动事件逻辑删除并递增版本 |
| GAME-06 | 分页复盘和提示 | 重放结果与存档一致，提示使用次数记录 |

模式：`TRAINING` 默认，机器人使用确定性合法启发式行动；`OPTIMAL` 不等待定时证明任务，每个机器人回合直接对当前完整局面执行带预算的 Minimax 求解。求解返回 `PROVEN` 才允许落子，预算内无法证明时返回 `robotStatus=NEEDS_PROOF`，不能静默切换为启发式。定时证明任务继续用于残局库的证明结果和策略展示。用户可选先手或后手；首个行动必须出牌，之后双方均可 PASS。

`legal-moves/search` 返回规则上的全部合法行动，另标行动证明状态；不以策略未覆盖为由阻止合法的人类行动。状态接口返回 allowedActions，例如 PLAY/PASS/HINT/ABANDON/RESTART/RESUME，前端结合其展示。OPTIMAL 在已知必败局面仍要求精确胜负，但不承诺“抵抗最久”；可在同等收益的合法行动中稳定选择。

人类提交 `expectedStateVersion` 和 `Idempotency-Key`。每个有效行动 stateVersion +1；出牌/不出事件写入同一事务，机器人使用相同领域入口。连续两个机器人行动分别提交，便于复盘与前端展示。

当前 V1 重开支持 ACTIVE/FINISHED/ABANDONED：在同一对局内恢复创建时保存的初始快照，历史行动事件做逻辑删除并递增 stateVersion；机器人旧任务通过版本条件自然失效。后续若需要跨局审计，再增加父子对局快照链。普通创建并不替换其它对局，但每用户最多 5 个 ACTIVE；弃局后可释放名额。

提示只在用户回合允许。当前 V1 在 HTTP 请求内同步读取完整局面，复用规则引擎枚举并返回一条确定性的规则合法建议 `HintResponse`；`proofStatus` 固定为 `UNKNOWN`、`winnerSide` 固定为空，不得将建议展示为必胜或最优。提示本身不改变局面版本、不写入 `game_action`，仅将 `hintCount` 加一。接口仍要求 `Idempotency-Key`，但当前实现只完成请求头校验和版本 CAS，幂等记录持久化及相同 Key 重放响应属于后续补齐项。未来异步求解可用 `solve_task(purpose=HINT)` 扩展，但必须绑定不可变状态快照和状态版本。

数据：game_session、game_action、game_bot_job；API：[game](../../api/game.md)。

复盘页面通过 `/api/games/replay/detail` 读取当前对局初始快照和行动事件分页；服务端只允许对局所有者读取，前端按事件中的 `afterState` 展示每一步，不将复盘结果作为新的状态写回。
# 开局交换先后手

创建对局前允许选择交换。服务端交换双方初始手牌并取反先手，生成新的本局快照；原残局版本、原始证明和题库数据不变。交换后 USER 仍固定为座位 0，BOT 仍固定为座位 1，因此可将原 USER 必胜残局转换为 BOT 使用原 USER 必胜手牌出牌。
